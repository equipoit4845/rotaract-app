# Kernel API Consumption Validation

Adversarial audit of the Kernel API consumption layer in `apps/mirotaract-web`, run against `kernel-openapi.yaml` directly (not against the prior implementation summary). Every claim below was verified by reading the actual source, running the real scripts, or writing a test that fails on the old code and passes on the fixed code.

## Executive Summary

**PASS WITH FINDINGS.** OpenAPI coverage, service-only isolation, and generated types are correct. Five **P1** defects were found and fixed (idempotency/correlation loss on retry, unhandled network errors, a dead-end active-organization selector, a logout/refresh race that could resurrect a cleared session, and a missing session-bootstrap-on-load — the last one meaning **every page reload silently logged the user out** despite a valid refresh cookie). Two **P2** and four **P3** issues were found; all but the request-timeout gap were fixed. All fixes are covered by new regression tests. Final state: 17/17 tests, clean lint/typecheck, clean production build.

## OpenAPI Coverage

Computed from `kernel-openapi.yaml` directly (`grep`-based operation extraction, not the implementation's own claim):

| | Count |
|---|---|
| Total operations | 117 |
| Browser-facing (no `x-service-only`) | 107 |
| `x-service-only: true` | 10 |
| Browser ops implemented | **107 / 107** |
| Service-only ops referenced anywhere in `apps/mirotaract-web` | **0** |
| Missing / duplicated / wrong-method mappings | 0 |

103 of the 107 map 1:1 to a `httpClient.METHOD("path", ...)` call in a `*.api.ts` file. The remaining 4 (`authenticateAccount` / `POST /auth/login`, `refreshSession` / `POST /auth/refresh`, `revokeSession` / `POST /auth/logout`, `revokeAllSessions` / `POST /auth/logout-all`) are — correctly — routed through the `/api/auth/*` BFF route handlers instead of `httpClient`, since only those four touch the refresh token. Verified by matching every `fetch(\`${kernelBaseUrl()}/auth/...\`)` call in `src/app/api/auth/*/route.ts` against the operation's real path.

Service-only isolation: `grep -rn "service-only|serviceAuth|/service/|introspect|serviceToken|KernelClient|kernel-sdk"` across `src` returns zero hits outside `client/schema.ts`. `schema.ts` does type the `/service/*` paths (it mirrors the whole spec), but it contains **zero runtime exports** (`export const|function|class|enum` count: 0) — pure `type`/`interface` declarations erased at compile time, contributing 0 bytes to the bundle. Confirmed with a static test (`test/service-only-exclusion.test.mjs`) that also asserts the public barrel `src/lib/api/index.ts` never mentions "service" or "introspect".

## Generated Types

`src/lib/api/client/schema.ts` is generated by `pnpm api:types` (`openapi-typescript ../../kernel-openapi.yaml -o ./src/lib/api/client/schema.ts`). Domain `*.types.ts` files derive from `components["schemas"]` / `operations` — no hand-written DTO duplicates a schema (the only manual types are request-option shapes like `PersonFilters` that don't exist in OpenAPI as objects).

**Finding (fixed):** running `pnpm api:types && git diff` produced an 11k-line diff. Cause: an earlier blanket `prettier --write` had reformatted the generated file (different comment/quote style), so the file checked in no longer matched the generator's canonical output — meaning `lint` and `api:types` would fight each other on every future regeneration. Fixed by adding `apps/mirotaract-web/.prettierignore` excluding `src/lib/api/client/schema.ts`, and regenerating it fresh. Re-verified: two consecutive `pnpm api:types` runs now produce byte-identical output (`md5sum` match), and `pnpm lint` passes.

## Authentication & Token Security

- Access token: in-memory only (`token-manager.ts`), never in `localStorage`/`sessionStorage`. Static test confirms `tokenManager`'s public surface has no member matching `/refresh/i`, and that no client-side file (excluding `.server.ts` and the BFF routes) references `refreshToken`.
- Refresh token: only ever touched by `session-cookie.server.ts`, which now carries `import "server-only"` (was missing — Next.js would previously only catch an accidental client import at bundle time via convention, not a hard build failure). The `server-only` package was added as a dependency.
- Cookie flags: `httpOnly: true`, `secure` in production, `path: "/api/auth"`. **Fixed:** `sameSite` was `"lax"`; changed to `"strict"` — this cookie is only ever read by our own same-origin `fetch()` calls, never as part of a cross-site top-level navigation, so `lax`'s extra allowance bought nothing and `strict` closes it for free.
- **P1 fixed — no session bootstrap.** Nothing in the app ever called `refreshManager.refresh()` on mount. Since `tokenManager` is memory-only by design, and `useCurrentUser()` is `enabled: isAuthenticated()`, **every page reload or new tab started fully logged out** regardless of a valid refresh cookie — the session could never reconstruct itself. Added `src/lib/api/auth/session-bootstrap.tsx` (mounted once in `QueryProvider`), which calls `refreshManager.refresh()` on first render; a visitor with no cookie gets a fast, silent no-op (the BFF route short-circuits with 401 before ever calling the Kernel).

## Refresh Concurrency

- **Single-flight, verified by test** (`test/http-client.retry.test.mjs`): 3 concurrent mutations that all 401 trigger exactly **1** call to `/api/auth/refresh`, then each of the 3 retries exactly once.
- **Single retry, verified by test:** if the refreshed token is still rejected, exactly 2 kernel calls happen total (1 attempt + 1 retry) — no loop.
- **P1 fixed — Idempotency-Key/X-Correlation-Id were regenerated on every physical retry.** `apiRequest` used to call the same `() => httpClient.POST(...)` closure a second time on 401, which re-ran the request-building middleware and minted **new** UUIDs for both headers — silently defeating idempotency (a retried mutation was no longer provably "the same operation" to the Kernel) and breaking correlation tracing across the retry. Root cause: `http-client.ts:14-20` (pre-fix) set both headers unconditionally in `onRequest` with no memory of a prior attempt. **Fix:** moved retry entirely into the `onResponse` middleware (`http-client.ts:23-66`) — it clones the fully-headered `Request` *before* the original `fetch()` consumes its body (`inFlight.set(id, request.clone())`, keyed by openapi-fetch's own per-call `id`), and on 401 replays that exact clone via a raw `fetch()` that bypasses the middleware pipeline entirely (so it can't retry itself again — no guard flag needed). Verified by test: the set of `(idempotencyKey, correlationId)` pairs on the 3 original attempts is byte-identical to the set on the 3 retries.
- **P1 fixed — network failures bypassed `KernelApiError` entirely.** `apiRequest` only handled openapi-fetch's `{error}` result; a thrown `fetch()` exception (offline, DNS, CORS) rejects the promise instead, which propagated as a raw `TypeError` to every caller — meaning `KernelApiError.network()` was dead code, never invoked, despite being part of the claimed error-normalization contract. Fixed with a `try/catch` around the call in `apiRequest` (`http-client.ts:85-96`). Verified by test.
- **P1 fixed — logout racing an in-flight refresh could resurrect a cleared session.** If a 401-triggered refresh was in flight and the user logged out before it resolved, the refresh's `tokenManager.setSession(...)` would fire *after* `clearSession()`, silently re-authenticating a user who had just explicitly logged out. Fixed with a monotonic `epoch` counter on `tokenManager` (`token-manager.ts:22,35,41,48`); `refresh-manager.ts` captures the epoch before its fetch and discards the result if the epoch moved (`refresh-manager.ts:26-45`). Verified by test (`test/session-race.test.mjs`): logout during a pending refresh leaves the session cleared even after that refresh resolves successfully.

## Error Handling

`KernelApiError` (`api-error.ts`) preserves `status`, `code`, `title`, `detail`, `instance`, `traceId`. **Fixed:** `type` (the RFC 9457 URI field, `required` in the OpenAPI `Error` schema) was silently dropped — added as a field. `isInvalidTransition` correctly keys off the stable `code`, not `title`/`detail` (verified by test with a non-English title). No component/hook anywhere reads `error.response` or another Axios/fetch-shaped structure — `grep` for that pattern across `src` returns nothing (there are no components yet, so this is trivially true, but the pattern doesn't exist in the API layer's own internals either, outside `api-error.ts`/`http-client.ts` themselves).

## Domain Coverage

All 11 domains (`auth, persons, organizations, memberships, periods, positions, appointments, authorization, applications, transfers, modules`) have `*.types.ts` / `*.keys.ts` / `*.api.ts` / `*.hooks.ts` — verified structurally (44/44 files present) and by the OpenAPI coverage matrix above (every domain's operations resolve to a real `httpClient` call).

## Query Keys

Deterministic and hierarchical — verified by test (`test/query-keys.test.mjs`): same filters serialize to the same key, different filters produce different keys, `organizationKeys.detail(id)` is a strict array-prefix of `children/ancestors/descendants(id)` (so invalidating detail cascades), and per-organization membership lists don't collide across organizations. No inline `queryKey: [...]` literals were found outside a `*.keys.ts` factory (grep across `*.hooks.ts` for `queryKey: \[` matches only calls into a `*Keys.*` factory).

## Mutation Invalidation

**P2 fixed — effective-permissions cache wasn't invalidated by mutations that can change authorization.** The OpenAPI spec itself documents that `activateAppointment`/`revokeAppointment` can materialize or revoke a derived `RoleAssignment` (CA-APP-02/05), that `closePeriod` ends active appointments in the same transaction (CA-PER-04), and that approving an application or completing a transfer creates/moves a membership (CA-SOL-02, CA-TRA-04/05) — all of which can change what `useCan()`/`useEffectivePermissions()` should report, but none of the corresponding mutation hooks invalidated `authorizationKeys.allEffectivePermissions()`. Added a new `authorizationKeys.allEffectivePermissions()` factory method (replacing an ad-hoc inline array literal that existed only in `useGrantRole`/`useRevokeRole`) and wired the invalidation into:

| Mutation | Now invalidates (in addition to its own domain) |
|---|---|
| `useActivateAppointment` / `useEndAppointment` / `useRevokeAppointment` / `useMarkAppointmentElected` / `useCreateAppointment` | `authorizationKeys.allEffectivePermissions()` |
| `useActivatePeriod` / `useClosePeriod` / `useSchedulePeriod` / `useCancelPeriod` | `appointmentKeys.currentAuthorities`, `authorizationKeys.allEffectivePermissions()` |
| All membership transitions (`activate/leave/resume/deactivate/graduate/reactivate/update/create`) | `authorizationKeys.allEffectivePermissions()` |
| `useApproveMembershipApplication` (membership-affecting branch only) | `membershipKeys`, `authorizationKeys.allEffectivePermissions()` |
| `useCompleteMembershipTransfer` (membership-affecting branch only) | `membershipKeys`, `authorizationKeys.allEffectivePermissions()` |

None of this is `queryClient.invalidateQueries()` called with no key (a full-cache wipe) — every invalidation is scoped to the specific domain(s) plausibly affected, matching the pattern already established elsewhere in the codebase (e.g. `useLogout` clearing the whole cache is the one legitimate exception, since a session boundary invalidates everything by definition).

**Not fixed (P3, judgment call):** these invalidations target *all* cached effective-permissions entries rather than just the affected person's, because the mutated resources (`Appointment`, `OrganizationMembership`) don't carry a `personId` directly (only `membershipId`), and resolving that would need an extra lookup. Broad-but-domain-scoped invalidation was judged safer than adding that indirection speculatively; flagged for a future pass if `useEffectivePermissions` traffic ever becomes a hot path.

## Authorization (`useCan`)

Confirmed **not** "1 button = 1 request": `useCan(permission, scope)` calls `useEffectivePermissions(personId, {organizationId})`, and TanStack Query dedupes identical query keys — every `useCan()` call on a screen with the same `(personId, organizationId)` shares one cached/in-flight request (`authorization.hooks.ts:63-71`). No `isPresident`/`role ===`/`title ===` legacy-authorization patterns exist anywhere (`grep` confirms; there's no legacy code in this repo to begin with — the "Appointment is the only source of truth for who holds a position, no isPresident flags" invariant from the OpenAPI spec is called out explicitly in a doc comment on `useCurrentAuthorities`).

## Client/Server Boundaries

- Every file under `src/lib/api/*/*.hooks.ts`, `use-active-organization.ts`, and `use-is-authenticated.ts` starts with `"use client"` (verified for all 13 files).
- `session-cookie.server.ts` now hard-fails a client-side import via `import "server-only"` (previously relied only on Next.js's file-naming convention, which doesn't fail the build on misuse).
- Route handlers (`src/app/api/auth/*/route.ts`) run server-side only by construction (App Router convention); confirmed no client component imports from `app/api/auth/*`.
- Production build output confirms the boundary holds in practice: `/api/auth/*` routes are listed as dynamic (`ƒ`) server routes, and the client bundle (`First Load JS`) contains no reference to the Kernel base URL string beyond the public `NEXT_PUBLIC_KERNEL_API_URL` env substitution, which is intentionally public.

## Security

- No `console.*` anywhere in `src/lib/api` or `src/app/api` (grep confirms zero matches) — nothing can leak a token/header/password through logging because nothing logs at all yet in this layer.
- `localStorage` usage is limited to exactly one non-sensitive value: the active-organization **id** string (`use-active-organization.ts`) — never a token, never an object.
- SameSite hardened to `strict` (see Authentication section).
- CORS: not applicable — the browser only ever talks to same-origin `/api/auth/*`; all other Kernel calls go directly cross-origin via `fetch` with the Kernel's own CORS policy governing that (outside this layer's control, correctly not duplicated here).

## Idempotency & Correlation

Both **fixed and covered by regression test** — see "Refresh Concurrency" above. A retried request now reuses the exact same `Idempotency-Key`/`X-Correlation-Id` as its original attempt.

**Not fixed (P3, informational):** `Idempotency-Key` is still auto-attached to `/auth/register`, `/verify-email`, `/forgot-password`, `/reset-password`, and `/invitations/accept` even though the OpenAPI header description exempts "Auth flows" from the requirement. This isn't forbidden by the spec (the header is opt-in convenience, not blocked on exempt endpoints) and causes no functional issue, so it was left as-is rather than special-cased.

16 pre-existing/added unit tests plus a dedicated race test (17 total), all genuinely exercising the real modules (not the file-content-regex style of the original scaffolding test) — `pnpm test` now runs via `tsx --test` (was `node --test`, which **could not actually execute** any of these tests: Node's native loader doesn't resolve TypeScript's extensionless relative imports even with `--experimental-strip-types`, confirmed by reproducing the failure before switching). Coverage added this pass:

- `test/http-client.retry.test.mjs` — single-flight refresh, single retry, idempotency/correlation preservation, network-error normalization (4 tests)
- `test/session-race.test.mjs` — logout-during-refresh race (1 test)
- `test/api-error.test.mjs` — Problem Details normalization, code-based (not message-based) transition detection, malformed-body fallback (3 tests)
- `test/token-isolation.test.mjs` — refresh token never referenced client-side, `server-only` guard present (3 tests)
- `test/service-only-exclusion.test.mjs` — no `/service/*` path or service-only operationId referenced outside the generated schema, barrel stays clean (2 tests)

**Not covered (would need a DOM/React renderer, e.g. `@testing-library/react`, not currently a dependency):** `useActiveOrganization`'s fallback-recovery effect and `SessionBootstrap`'s mount effect. Both were fixed by direct code trace against the specific failure scenarios in the request (revoked/transferred membership; reload with a valid refresh cookie) and verified via `typecheck`/`build`, but not by an automated render test. Flagged as remaining technical debt below rather than silently claimed as tested.

## Findings

### P1

1. **Idempotency-Key/X-Correlation-Id regenerated on retry** — `src/lib/api/client/http-client.ts`. Fixed (request-clone + `onResponse`-level retry). Verified by test.
2. **Network failures not normalized to `KernelApiError`** — `src/lib/api/client/http-client.ts:85`. Fixed (`try/catch` in `apiRequest`). Verified by test.
3. **`useActiveOrganization` never recovers from a stale/revoked/transferred selection** — `src/lib/api/organizations/use-active-organization.ts`. The old fallback effect only ran when there was *no* selection at all, not when the current one stopped being valid — a user whose membership in their active org was revoked would see `organization: undefined` forever, with valid memberships elsewhere never picked up. Fixed (effect now re-evaluates against `status === "ACTIVE"` memberships on every `currentUser`/`organizationId` change).
4. **Logout racing an in-flight refresh can resurrect the session** — `src/lib/api/client/{token-manager,refresh-manager}.ts`. Fixed (session `epoch`). Verified by test.
5. **No session-bootstrap-on-load — every reload/new-tab appeared logged out** — missing entirely; added `src/lib/api/auth/session-bootstrap.tsx`, wired into `providers/query-provider.tsx`.

### P2

6. **Effective-permissions cache not invalidated by appointment/period/membership/application/transfer mutations** — 5 files, see Mutation Invalidation table. Fixed.
7. **`pnpm api:types` was not actually reproducible** — a prior `prettier --write` pass had reformatted the generated `schema.ts`. Fixed (`.prettierignore`).

### P3

8. **`session-cookie.server.ts` missing `import "server-only"`** — fixed, package added.
9. **Refresh cookie `sameSite: "lax"` where `"strict"` is safe and strictly better** — fixed.
10. **`KernelApiError` silently dropped the Problem Details `type` field** — fixed.
11. **Test runner couldn't execute its own tests** — `node --test` doesn't resolve extensionless TS imports even with `--experimental-strip-types`; switched to `tsx --test`.
12. **No default request timeout** — `src/lib/api/client/http-client.ts`. A hung request with no server response relies entirely on component unmount or query invalidation to resolve; there's no intrinsic bound. **Not fixed** — the correct timeout duration is a product decision, not a mechanical bug fix; recommend `AbortSignal.any([callerSignal, AbortSignal.timeout(N)])` once a value is chosen.
13. **Effective-permissions invalidation is domain-broad, not person-scoped** — see Mutation Invalidation. Not fixed; documented trade-off, not a correctness bug.
14. **`as never` casts around a handful of untyped-`object` OpenAPI schema fields** (`memberships.api.ts`, `modules.api.ts`) — pre-existing, contained to those exact call sites, each with an inline comment explaining the openapi-typescript limitation. Not a defect, left as-is.

## Remaining Technical Debt

- No request timeout (P3-12, above) — needs a product-level duration decision.
- Effective-permissions invalidation is domain-broad rather than person-scoped (P3-13).
- `useActiveOrganization`'s fallback-recovery and `SessionBootstrap`'s mount effect are fixed by code trace but have no automated render test — adding one would require introducing `@testing-library/react` (or equivalent), which wasn't added in this pass since it's a new test-infra dependency, not a mechanical fix.
- No components exist yet in `apps/mirotaract-web`, so several checks (barrel-import violations, `.tsx`-level client/server misuse) are currently trivially true rather than actively defended against real usage — worth re-running this audit once real screens land.
